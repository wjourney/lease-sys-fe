## 1. 技术方案

| 范围       | 采用方案                                                       |
| ---------- | -------------------------------------------------------------- |
| 包管理     | 前后端分别使用 pnpm，分别提交 lockfile                         |
| 前端       | React + TypeScript + Vite + Ant Design + React Router          |
| 状态与请求 | MobX + mobx-react-lite + Axios                                 |
| 表单与样式 | AntD Form、ConfigProvider 主题、Tailwind CSS 工具类             |
| 后端       | NestJS + TypeScript，单应用按业务模块划分                      |
| 数据访问   | PostgreSQL + Prisma；特殊数据库约束用 SQL migration            |
| API        | REST `/api/v1` + OpenAPI 文档；据此生成前端接口类型            |
| 文件       | materials 保存元数据；开发使用本地私有目录，生产接私有对象存储 |
| 合同及发票 | HTML 模板渲染 PDF，保存业务快照及生成状态                      |
| 定时处理   | 后端出账及重试任务，依赖数据库锁和唯一键防重                   |

初始化时核对 Node、pnpm 和依赖的兼容版本并锁定，不在计划中假定尚未验证的最新版组合。首版不增加 Redis、消息队列、微服务或独立 BFF；需要分页、筛选的数据仍由数据库查询。

## 4. MobX 与缓存策略

- RootStore 通过稳定的 React Context 提供实例，业务组件使用 mobx-react-lite 的 observer。
- AuthStore 保存当前用户、角色和后端返回的能力；SettingsStore 保存字典和公共选项。
- 模块 store 保存需跨组件复用的列表、详情、请求状态及筛选状态；筛选和分页也写入 URL，便于返回与刷新。
- 表单草稿使用 AntD Form；弹窗开关等局部状态用 React state，不把全部状态塞进 MobX。
- MobX 本身不会自动提供请求去重、过期和失效策略，统一 request/cache helper 实现这些规则，避免每个页面复制。

建议首版策略：

| 数据                     | 缓存策略                                                     |
| ------------------------ | ------------------------------------------------------------ |
| 单位类型等字典           | 内存缓存建议 5 分钟，修改设置后主动失效                      |
| 项目／单位列表           | 按用户、权限范围、筛选、排序、页码形成 key；短缓存建议 30 秒 |
| 普通详情                 | 按 ID 缓存，修改成功后失效或使用服务端新结果更新             |
| 财务详情及可支付金额     | 打开详情和操作前重新取数；提交时后端再次锁定校验             |
| 密码、资金数据和个人资料 | 不将业务缓存持久化到 localStorage                            |

缓存 TTL 属于初始实现参数，可配置。相同进行中请求复用 Promise；筛选切换取消旧请求或用请求序号避免旧结果覆盖。收款确认等写操作不做无条件自动重试，服务端接受幂等键。退出、换账号或权限变化清空对应 store 和缓存。

操作成功后按业务影响失效：收款确认刷新应收详情及订单状态；佣金支付刷新佣金及支出；修改项目／单位刷新相关列表。财务数据不做提前显示成功的乐观更新。

AntD Table 等第三方组件接收普通数据快照；在 observer 边界读取所需字段，避免传入未被第三方组件观察的可变 observable 后页面不更新。路由按页面懒加载，独立请求并行，列表后端分页，重型 PDF 预览按需加载。

## 5. 后端结构

```text
src/
  main.ts
  app.module.ts
  common/
    guards/            登录、动作权限
    filters/           统一异常输出
    dto/               分页、错误等公共协议
    services/          业务历史追加、数据范围辅助
  database/            Prisma 服务
  modules/
    auth/
    users/
    sales-companies/
    projects/
    units/
    orders/
    incomes/
    expenses/
    commissions/
    invoices/
    materials/
    fund-accounts/
    settings/
  jobs/                周期出账、PDF 生成、发送重试
```

Controller 处理路由与 DTO；Service 处理业务、权限范围和事务；Prisma 负责持久化。不额外引入一层通用 Repository 模板。Auth、Jobs 是代码模块，不因此增加数据库表。

DTO 验证使用明确字段白名单，创建／更新／确认各有独立 DTO。客户端不能自行设置确认人、销售归属、operation_logs 或任意业务状态。通用 PATCH 不能绕过收款确认、付款登记等动作接口。

## 6. 接口协议

统一 `/api/v1` 前缀，普通资源提供列表、详情、创建、更新与受限制的删除；特殊业务使用动作接口。

| 业务         | 关键接口示例                                                                                                           |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| 登录         | POST /auth/login；POST /auth/logout；GET /auth/me                                                                      |
| 账号／公司   | /users；/sales-companies；/sales-companies/:id/users                                                                   |
| 项目／单位   | /projects；/units；GET /projects/:id/units                                                                             |
| 订单         | /orders；PATCH /orders/:id；POST /orders/:id/terminate；POST /orders/:id/handover；POST /orders/:id/deposit-settlement |
| 收入主记录   | GET/POST /incomes；GET/PATCH /incomes/:id                                                                              |
| 分次收款     | GET/POST /incomes/:id/receipts；POST /incomes/:id/confirm；POST /incomes/:id/reject                                    |
| 支出         | /expenses；POST /expenses/:id/pay                                                                                      |
| 佣金         | /commissions；POST /commissions/:id/payments                                                                           |
| 发票         | /invoices；POST /invoices/:id/void；POST /invoices/:id/reissue；POST /invoices/:id/send                                |
| 文件资料     | /materials；GET /materials/:id/download；GET /materials/:id/versions                                                   |
| 设置及账户   | /settings/unit-types；/fund-accounts                                                                                   |
| 行内操作历史 | GET /orders/:id/operations 等所属模块接口，读取该行 operation_logs                                                     |

收入列表默认仅返回 RECEIVABLE；receipts 接口仍写同一张 incomes，后端固定创建 RECEIPT 和 parent_id，确认／驳回接口只接受收款行。接口资源名称不等于数据库必须拆表。

列表返回 `{ items, total, page, pageSize }`；日期采用明确 ISO 格式，金额以十进制字符串传输。错误使用 HTTP 状态码加 `{ code, message, fieldErrors?, requestId }`。分页上限、排序字段白名单、筛选字段白名单由后端约束。并发修改携带 revision，版本冲突返回 409，让用户刷新后重试。

OpenAPI 作为前后端接口契约，生成客户端类型；Prisma 实体不直接暴露为前端响应，避免返回密码哈希、操作历史或未授权财务字段。

## 7. 五角色与数据权限

以下为实施权限基线，具体按钮以 PDF 和已确认的业务限制校准；未明确授予的写权限默认关闭，不根据页面可见性推断写权限。

| 角色           | 默认职责及数据范围                                                   |
| -------------- | -------------------------------------------------------------------- |
| 超级管理员     | 平台管理、账号与公司、配置、全量业务；关键财务动作仍执行相同金额约束 |
| 内部运营       | 项目、单位、订单、资料及相应查询；不执行财务确认和付款               |
| 内部财务       | 收入确认、费用付款、佣金录入及支付、发票、资金账户；查询关联订单资料 |
| 销售公司管理员 | 本公司成员管理、本公司订单与佣金，以及获准查看的项目／单位资料       |
| 销售员工       | 本人负责的订单、佣金及允许登记的收款，获准查看的项目／单位资料       |

授权分为角色／动作、业务数据范围、字段三个层次。后端同时保护列表、详情、统计、导出、文件下载；不能仅靠隐藏前端菜单。销售公司管理员不能把自己改成内部角色，成员创建归属由服务端固定为本公司。

历史订单保存当时销售公司及负责销售的归属，不因账号调动而改写。精确租金不可见时后端不返回字段，也限制利用排序、筛选、统计反推该字段。收入收款行通过父应收判断权限，文件通过其直接业务归属判断权限。

## 8. 关键业务实现

### 下单、改单及占用

创建订单锁定单位或使用数据库租期排斥约束，检查有效占用区间，保存租客、单位、销售及价格快照，生成首期应收和押金应收。未来租金按 orders 的付款周期和提前出账天数生成，不重复建计划表。

首期实际付款登记后锁住普通录单编辑；授权修改仍可直接生效，不走申请审批。租期修改检查占用；租金等修改只作用后续规则，已出账历史通过明确财务调整处理，已确认款项和发票不回写。退租、交还、财务结清分别判断。

### 收款及开票

一条 RECEIVABLE 可关联多条 RECEIPT。登记或确认时锁定应收主记录，计算有效应收减已确认和待确认金额，防止重复或超额登记。确认同一收款只能执行一次；确认租金与押金收齐后更新订单生效状态。

确认事务中创建对应的待生成发票记录；PDF 在事务后生成，失败保留已确认收款事实并允许重试。发票只关联已确认 RECEIPT，同一笔收款最多一个有效发票版本。明确配置 render_attempts、render_next_retry_at 等重试字段，不建立额外任务表。

### 支出、佣金及押金

普通费用一条 expenses 保存应付及一次全额实付，支付登记不能重复。佣金每期一条 commissions，财务填写金额；各次付款生成或完成对应 expenses，锁定佣金校验已付和待执行计划。待付佣金和其支出计划不能在报表中重复相加。

押金收款按押金类型区分，不计入租金收入指标；退款由 expenses 保存，并用 original_income_id 追溯原款项。扣除结果在 orders；扣除、退款及未执行退款计划合计不得超过可处理押金。收支数据仍需区分现金流、租金、押金、其他费用，避免将押金直接算作经营收入。

### 文件、合同和发票

每条 materials 直接归属一个业务记录，不采用资料父子结构。先保存所属业务，再通过已鉴权的上传接口写文件；失败允许重试，不能把未成功上传的文件标记为可用。可选临时上传由存储暂存和过期清理处理，不增业务表。

文件下载必须先校验业务权限，可由后端返回短效下载地址；私有文件不通过公开静态目录暴露。限定可接受文件类型和体积，文件名不作为可控服务器路径。业务软删除不立即删除物理文件，清理前检查引用。

合同使用模板和签约快照生成版本，单位或模板后续修改不能改变已签合同。发票 PDF 同理。邮件通过配置的服务商发送，发送状态及重试计划保存在 invoices；外部结果不明时先核对再重试。无邮件凭据时开发模式展示预览，不伪报已发送。

### 操作历史

各业务行的 operation_logs 仅保存增删改、操作人、时间、变化字段、原因、operation_id。业务写入与日志追加原子提交，使用 revision 或行锁防止数组覆盖。后端生成日志，客户端不能直接写；不记录密码、令牌和密钥。列表默认不返回日志，详情按需查询。

删除采用软删除以保留该行历史；有资金事实的记录不可通过软删除绕过财务状态或统计。账号停用、类型停用、已开票记录的作废遵循各自业务约束。

## 9. 登录、运行与部署

建议浏览器与 API 同源部署：静态资源由 Nginx 服务，`/api` 转发 NestJS。登录凭据使用 HttpOnly Cookie 承载 JWT，生产启用 Secure、合适的 SameSite、写请求 CSRF 防护和来源校验；本地用 Vite 代理保持同源开发体验。

密码使用成熟的自适应哈希实现。服务端每次请求校验账号、公司有效状态及 users.auth_version，停用、退出和重置密码提升版本使旧凭据失效。首版令牌到期重新登录；如后续需要续期，再增加明确会话策略，不临时把长效令牌存 localStorage。登录接口限速，401 在前端统一处理，避免多次弹出登录。

本地 PostgreSQL 通过 Docker Compose 提供，后端与前端分别启动。迁移后运行 seed 只创建 admin 超级管理员账号；业务数据由用户录入。集成测试所需数据仅在独立的 `lease_test` 数据库中临时生成，并在测试结束后清除。

生产先采用一个 NestJS 实例、一个 PostgreSQL 和文件存储。定时出账、PDF 和邮件重试使用数据库领取／锁及幂等键；多实例运行时必须保持同样的防重机制。数据库和文件存储做备份，数据库迁移纳入发布流程。环境配置包含数据库连接、认证密钥、站点地址、存储、邮件和业务时区，密钥不提交仓库。

## 10. 开发顺序及验收

| 阶段            | 交付内容                                                               | 验收重点                               |
| --------------- | ---------------------------------------------------------------------- | -------------------------------------- |
| 1. 基础工程     | pnpm 工程、主题布局、NestJS、数据库迁移、OpenAPI、登录与五角色种子数据 | 五角色能登录，权限和数据范围可验证     |

| 4. 财务闭环     | 分次收款、确认驳回、支出、佣金、发票                                   | 金额不重复累计，重复提交和并发操作正确 |

| 6. 联调与交付   | 五角色页面核对、异常状态、部署说明和备份配置                           | 主流程端到端通过，构建和类型检查通过   |

前后端按模块一起完成，先贯通“登录 → 单位 → 下单 → 应收 → 收款确认 → 发票”的可操作流程，再补齐其他模块。业务数据库初始化时只保留 admin；自动化测试所需 fixture 仅在独立测试库临时生成。

重点测试：跨公司和个人数据隔离、文件越权、单位租期并发冲突、同表收入父子类型、并发超收、重复确认、佣金超付、押金超退、有效发票唯一和重开、周期重复出账、operation_logs 并发追加、财务记录软删除限制。后端使用真实 PostgreSQL 集成测试验证约束与事务；前端用组件测试及浏览器端到端验证五角色主路径。简单样式调整不额外编写镜像式测试。

交付为可运行前后端、数据库迁移、admin 初始账号、接口文档、关键测试、环境变量示例及部署说明。生产存储／邮件供应商凭据和正式域名在部署阶段配置，不阻塞本地业务开发。
